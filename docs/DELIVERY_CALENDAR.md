# T156 Delivery Calendar Governance

The machine-readable schedule is [delivery_calendar.json](delivery_calendar.json). This is the schedule authority only. `IMPLEMENTATION_QUEUE.md` alone authorizes numbered work and records Done. Calendar entries never authorize tasks.

## Activation and arithmetic
Prospective enforcement starts at **T157**, inclusive. T1–T155 and bootstrap T156 are exempt; no fictional history is reconstructed. Schema versions 2 and 3 fix the project-local clock at **Asia/Kolkata**. All dates are ISO YYYY-MM-DD project-local dates. Durations are **inclusive**: finish minus start plus one day. Finish variance is actual protected completion minus original planned finish in calendar days: negative **Early**, zero **On Time**, positive **Late**. The original planned finish is immutable for variance; forecasts may change independently. A Done task records the implementation protected-merge date, never a developer's last commit or the later closeout date.

## Schema V3 milestone completion provenance (T179)

Schema V3 preserves read compatibility for Schema V1 and V2 records. It adds a fail-closed contract only when a V3 milestone has a non-null `actual`; a null actual must have no `completion_provenance`, so authorizing this schema does not fabricate or reconcile completion.

A completed V3 milestone requires exactly one `completion_provenance` object. `accepted_at_utc` is converted with the fixed Asia/Kolkata clock and must produce both the milestone `actual` and `actual_completion`. `acceptance_scope` is an explicit boundary: only `internal_office_dogfooding` and `production_release` are supported. These values are not interchangeable: internal office-dogfooding acceptance is never production-release acceptance. The object must name a non-empty owner acceptance reference, a non-empty duplicate-free list of immutable evidence references, and a SHA-256 digest for the evidence package.

The completion object snapshots `baseline_at_completion`, `forecast_at_completion`, and `confidence_at_completion`. Each must match the milestone value recorded at completion; the validator derives `variance_days` and `variance_classification` from the frozen forecast and actual date. A later baseline, forecast, or confidence rewrite therefore fails validation rather than silently changing historical completion meaning. Supported confidence values are `low`, `medium`, and `high`.

T179 itself changes only the contract version. It does not set M1 `actual`, change a milestone baseline or forecast, reclassify the existing M1 internal office-dogfooding acceptance, or append history. Recording any milestone completion remains a separately authorized successor action.

## Forecasting
Schema version 2 distinguishes finish_to_start scheduling predecessors from defect_evidence references. Only finish-to-start edges affect forecast topology or cycle detection; evidence references preserve diagnostic provenance without making a task a completed predecessor. Independent lanes may overlap. Slack is the amount of delay absorbed without moving the milestone; the active critical path has zero slack. An early finish only accelerates a milestone when all controlling predecessor/successor and fixed-date constraints permit it. Recompute after each protected task completion, record every affected milestone including unchanged movement, and append an immutable old/new/movement/direction/trigger/reason/recalculation entry with a unique trigger key. Never replace prior entries. The forecast calculator accepts an explicitly complete task network; it must not claim a validated overall date from an incomplete future backlog.

## Required update protocol
Before authorizing T157+, add a structured task entry with all required planned/forecast/dependency/critical-path fields. The implementation PR remains Authorized with null completion fields. Once its protected merge is independently verified, a separate closeout records the auditable evidence tuple (implementation PR, merge SHA and parents, GitHub UTC merged_at, Asia/Kolkata conversion, QA publication head and actual-start evidence), actuals, variance and one history event per affected milestone. Queue, calendar and PROJECT_STATE completion tuple must synchronize atomically; validator failure blocks partial, stale or premature closeout. If the protected merge is recorded while closeout is pending, the validator reports it as an operational alert but never fabricates actuals. Calendar planning never changes the task ledger.

## Cancellation and successor provenance (T168)

For T157+ the queue Status cell is authoritative and permits exactly `Authorized`, `Done`, or terminal
`Cancelled`. A cancellation is represented only by the calendar task's `cancellation_evidence` object:
`cancelled_task_id`, `owner_approval_provenance`, ISO `cancellation_date`, non-empty `reason`, and
non-empty `evidence_reference` are mandatory. Its task ID must match the calendar record. This is
distinct from `completion_evidence`; a Cancelled task must contain neither completion evidence nor
actual start/completion/variance fields, so cancellation never invents calendar actuals or counts as
Done.

An optional `successor_task_id` is provenance, not authorization. Its `successor_state` records the
successor's state **at cancellation time** and is immutable historical evidence: an initially
`"proposed_unapproved"` successor remains so recorded even after it is independently Authorized or
Done. Current readiness is determined separately from the successor's own authoritative queue row,
which must be Authorized or Done whenever that row exists. A not-yet-created successor is valid only
with `successor_state: "proposed_unapproved"`; it remains non-executable planning context until
separately owner-authorized in the queue. `"authorized"` is invalid for an unknown successor.
Self-supersession, unsupported historical states, duplicate/top-level successor fields, and
current-status/evidence contradictions fail validation. A Cancelled task cannot be a finish-to-start
predecessor: scheduling edges require a completed predecessor. Defect-evidence references remain
provenance only and do not make cancellation or successor authorization implicit.
